# Nabla Constitution v0.1

**Статус:** утверждена владельцем проекта  
**Версия:** 0.1  
**Дата утверждения:** 2026-07-11  
**Область действия:** все выпускаемые версии Nabla, её официальные модули, клиенты, протоколы, миграции и автоматизированная разработка  
**Основание:** `Nabla Architecture Map v0.1`

# 0. Роль документа

Конституция определяет свойства Nabla, которые имеют приоритет над удобством отдельной реализации, конкретным технологическим стеком и границами очередной версии.

Её назначение — сохранить:

- владение пользователя своими данными;
- корректность и объяснимость накопленной информации;
- возможность локальной работы;
- восстановимость и переносимость;
- контролируемую расширяемость;
- ограниченные полномочия ИИ и внешнего кода;
- способность системы развиваться без регулярного переписывания фундамента.

Конституция не определяет:

- конкретный язык программирования;
- UI-фреймворк;
- физическую схему таблиц;
- формат IPC;
- конкретный алгоритм поиска, синхронизации или статистической модели;
- перечень экранов;
- календарный план разработки.

Эти решения принимаются в подчинённых документах при условии соблюдения настоящей Конституции.

После утверждения этого документа `ARCHITECTURE-1.md` сохраняется как исходная архитектурная карта. При расхождении нормативным является `CONSTITUTION.md`; расхождение должно быть явно устранено в следующем `ARCHITECTURE.md`, а не оставлено как неявное исключение.

# 1. Нормативный язык

В документе используются следующие термины:

- **MUST / ОБЯЗАН** — требование обязательно для совместимой реализации;
- **MUST NOT / НЕ ДОЛЖЕН** — действие запрещено;
- **SHOULD / СЛЕДУЕТ** — допустимо отступить только при документированной причине и анализе последствий;
- **MAY / МОЖЕТ** — разрешённый, но необязательный вариант.

Фраза без одного из этих маркеров поясняет смысл требования, но не создаёт самостоятельного исключения.

## 1.1 Основные термины

### Canonical state

Состояние, потеря которого приводит к необратимой потере пользовательской информации, её смысла, истории или доказательств совершённых действий.

К canonical state относятся как минимум:

- первичные факты;
- сущности и их ревизии;
- актуальные heads и tombstones;
- типизированные отношения;
- идентичность и метаданные пользовательских blobs;
- версионированные определения метрик, политик и конфигураций;
- необходимые записи аудита и происхождения данных.

### Предметное canonical state

Пользовательское или предметное canonical state: содержание, наблюдения, сущности, отношения, definitions и blobs, ради которых существует прикладная функция Nabla. Оно не включает служебные audit/evidence records, хотя последние также могут быть невосстановимым canonical state.

### Immutable fact

Неизменяемая запись о произошедшем наблюдении, действии или результате. Исправление факта не изменяет исходную запись, а создаёт новый факт.

### Revisioned entity

Изменяемый в пользовательском смысле объект со стабильной идентичностью, неизменяемыми ревизиями и одной или несколькими актуальными heads.

### Derived state

Индексы, projections, агрегаты, оценки моделей, кэши и другие данные, полностью восстанавливаемые из canonical state, версионированных определений и версии алгоритма.

### Operational state

Служебное состояние выполнения и транспорта: очереди, outbox/inbox, cursors, leases, checkpoints, состояния jobs и диагностика. Оно обслуживает корректность работы, но не является пользовательским предметным содержанием.

### Device-local state

Состояние, смысл которого ограничен одним устройством: пути, размеры окон, кэши, наличие локальной копии blob, прогресс загрузки и аналогичные данные.

### Secret

Ключ, токен, пароль или credential, раскрытие которого предоставляет полномочия либо нарушает конфиденциальность.

### Command

Типизированный запрос на изменение canonical state или выполнение контролируемого внешнего действия.

### Query

Типизированное чтение canonical или derived state, не изменяющее предметное состояние.

### Processor

Зарегистрированный обработчик, который после commit строит derived state либо выполняет ограниченную служебную работу.

### Capability

Версионированная атомарная возможность системы с явными schemas, полномочиями, ошибками и тестами.

### Module

Версионированный поставщик предметной логики и capabilities, объявленный через manifest.

### Loop

Проверяемый путь от создания информации через её преобразование и потребление к полезному результату, решению, действию, проверке, восстановлению либо прекращению ненужного сбора.

### Purge

Отдельная явно необратимая процедура физического уничтожения выбранных данных и доступных копий, насколько это технически возможно.

# 2. Классы состояния и область требований

Каждая сохраняемая запись и каждое поле MUST быть отнесены ровно к одному основному классу в `DATA-CLASSIFICATION.md`.

| Класс | Источник истины | Допустимый путь записи | Восстановимость | Обычный export |
|---|---|---|---|---|
| Предметные canonical facts | Да | Command | Не предполагается | Да |
| Revisioned entities | Да | Command | Не предполагается | Да |
| Relations и blob identity | Да | Command | Не предполагается | Да |
| Audit и evidence records | Да | Kernel Audit Service внутри контролируемого workflow | Не предполагается | Отдельно, с privacy-редакцией |
| Derived state | Нет | Зарегистрированный processor или ограниченный Kernel Service | Обязательна | Не обязателен |
| Operational state | Нет | Ограниченный Kernel Service | Может быть частичной | Не требуется |
| Device-local state | Нет | Локальный прикладной или Kernel Service | Не требуется | Не требуется |
| Secrets | Нет | Выделенный Secret Service | Восстановление определяется политикой ключей | Запрещён по умолчанию |

Blob-файл может быть canonical пользовательским содержанием, тогда как факт его наличия на конкретном устройстве является device-local state.

Если значение невозможно полностью восстановить и его потеря меняет пользовательскую историю или смысл данных, оно MUST классифицироваться как canonical, даже если первоначально считалось кэшем.

Структурные поля, необходимые только для целостности, адресации, безопасности или миграции, не обязаны иметь пользовательский decision loop, но MUST иметь документированное техническое назначение, владельца и retention policy.

# 3. Архитектурные инварианты

## I1. Единственный контролируемый путь изменения

1. Любое изменение предметного canonical state MUST выполняться через зарегистрированный Command API.
2. Append-only audit и evidence records MAY создаваться только Kernel Audit Service внутри выполнения command, security-relevant query или административного workflow.
3. UI, ИИ, импортёры, sync-адаптеры, модули и фоновые задачи MUST NOT писать canonical tables или blobs напрямую.
4. Удалённое изменение, полученное через sync, MUST применяться через типизированную sync-команду с теми же проверками идентичности, версии, разрешений и идемпотентности.
5. Processor MAY изменять только объявленный derived или operational state. Если результат processor должен стать canonical fact, processor MUST отправить отдельную command.
6. Query MUST NOT изменять предметное canonical state. Ограниченные записи query-cache и diagnostics MAY выполняться только через Kernel Services; обязательный security audit создаётся по правилу пункта 2.
7. Schema migration, restore и purge являются привилегированными административными workflows, а не обходом Command API. Они MUST иметь:
   - явную версию;
   - эксклюзивное владение writer;
   - предварительную проверку;
   - журнал выполнения;
   - план восстановления либо явную маркировку необратимости.
8. На каждом устройстве в каждый момент MUST существовать не более одного логического владельца записи в конкретное canonical хранилище.

**Проверка:** статический архитектурный тест обнаруживает записи в canonical storage вне разрешённых persistence-adapters; интеграционный тест доказывает, что UI, import, sync и AI проходят один и тот же policy boundary.

## I2. Первичные факты не переписываются

1. Immutable fact после commit MUST NOT редактироваться или заменяться обычной операцией.
2. Исправление MUST создавать новый correction fact, где направление ссылки однозначно: `correction.supersedes_id = original.id`.
3. Correction MUST содержать автора, время, причину и происхождение исправления.
4. Текущая интерпретация MAY выбирать последнюю применимую коррекцию, но исходная запись MUST сохраняться.
5. Технический статус обработки факта MUST храниться отдельно как operational или derived state и MUST NOT менять семантику исходного факта.
6. Физическое уничтожение факта допускается только процедурой purge в соответствии с I11.

**Проверка:** обычные permissions хранилища запрещают `UPDATE` и `DELETE` immutable facts; тест цепочки corrections восстанавливает полную историю.

## I3. Изменяемые сущности имеют неизменяемые ревизии

1. Revisioned entity MUST иметь стабильный `entity_id`.
2. Каждое содержательное изменение MUST создавать новую immutable revision.
3. Revision MUST ссылаться на родительскую revision или revisions.
4. Head является указателем на актуальную revision, а не местом хранения изменяемого содержимого.
5. Конкурирующие heads MUST сохраняться до автоматического или пользовательского разрешения конфликта; silent last-write-wins для пользовательского содержимого запрещён.
6. Undo MUST создавать новую операцию выбора head, новую revision либо компенсирующую command; прежние revisions не уничтожаются.
7. Обычное удаление MUST выражаться revision со статусом archived/deleted или tombstone.
8. Физическое уничтожение истории допускается только через purge.

**Проверка:** восстановление любой сохранённой revision воспроизводит её содержимое; конфликт двух descendants не теряет ни одну ветвь.

## I4. Производные данные полностью восстанавливаемы

1. Derived state MUST быть воспроизводим из:
   - конкретного набора canonical inputs;
   - версионированного определения;
   - версии processor, алгоритма или модели;
   - задокументированных параметров.
2. Удаление всех derived tables и indexes MUST NOT приводить к потере canonical информации.
3. Для каждого вида derived state MUST существовать rebuild procedure и тест её корректности.
4. Если внешний результат невозможно воспроизвести, но он имеет историческую или пользовательскую ценность, он MUST сохраняться как immutable fact с provenance, а не как derived cache.
5. Derived state MUST NOT синхронизироваться или экспортироваться как единственный источник истины.

**Проверка:** система восстанавливает derived state после его полного удаления и получает эквивалентный результат при одинаковых inputs и версиях.

## I5. Семантика данных версионируется

1. Изменение смысла поля, единицы измерения, допустимого диапазона, grain, missing policy, формулы, rubric, scheduler или модели MUST создавать новую semantic version.
2. Существующие raw values MUST NOT молча переинтерпретироваться под новую семантику.
3. Миграция MUST явно указывать, какие значения преобразованы, какие оставлены в старой версии и где преобразование необратимо.
4. Cosmetic rename MAY не создавать новую semantic version, если множество допустимых интерпретаций и результатов не меняется.
5. Каждое аналитическое значение MUST позволять определить использованные версии definitions и processors.

**Проверка:** изменение семантического контракта без повышения версии отклоняется schema- и compatibility-тестами.

## I6. Расширение выполняется через capabilities и доверенные модули

1. Новый предметный функционал MUST объявляться через versioned capability и module contracts.
2. Runtime MAY компоновать зарегистрированные capabilities, layouts, forms, queries, metrics и loops как декларативные данные.
3. Runtime MUST NOT генерировать, компилировать, интерпретировать или исполнять произвольный код, SQL либо shell-команды, полученные от ИИ, документа, пользователя или модуля данных.
4. До принятия отдельного ADR и реализации доверенного installation boundary исполняемые модули MUST быть встроенными compile-time packages с runtime activation.
5. Будущая загрузка исполняемого модуля MAY быть добавлена только через отдельный ADR и доверенный installation boundary, который обеспечивает:
   - проверяемое происхождение пакета;
   - hash и подпись;
   - совместимость версий;
   - manifest и минимальные permissions;
   - явное подтверждение установки;
   - изоляцию либо документированную модель доверия;
   - rollback и удаление без потери пользовательских данных.
6. Подписанный модуль не получает автоматического доверия ко всем данным; permissions capabilities остаются обязательными.
7. Универсальная capability вида `execute_arbitrary_operation` запрещена.

**Проверка:** неизвестный, неподписанный или несовместимый модуль не активируется; capability без manifest, owner и ограниченных permissions отклоняется.

## I7. Сохраняемая информация должна иметь доказанную полезность

1. Каждое предметное canonical поле MUST иметь активный либо явно наблюдательный loop.
2. Loop MUST объявлять producer, consumer, purpose, decision/action/outcome, collection cost, latency, retention, failure modes и acceptance test.
3. Поле не может быть оправдано формулировкой «может пригодиться позднее».
4. Наблюдательный loop без немедленного решения допускается только при наличии:
   - минимально необходимого покрытия;
   - даты или условия пересмотра;
   - критерия остановки сбора;
   - ограничения стоимости и чувствительности данных.
5. Структурные, audit-, operational-, transport-, device-local- и secret-поля MAY не иметь пользовательского loop, но MUST иметь:
   - техническое назначение;
   - владельца;
   - единственного допустимого writer;
   - retention или reset policy;
   - потребителя в integrity, security, recovery, diagnostics или transport workflow.
6. Если consumer исчезает, сбор поля MUST быть остановлен либо loop обновлён до следующего выпуска.

**Проверка:** Data Catalog и Loop Registry не допускают новое предметное поле без loop и новое служебное поле без технического обоснования.

## I8. Пользовательская функция должна завершаться полезным результатом

1. Каждый пользовательский экран, widget, form или workflow MUST иметь объявленный outcome.
2. Допустимыми outcomes являются как минимум:
   - сохранение или восстановление информации;
   - нахождение нужного содержания;
   - изменение понимания;
   - принятие решения;
   - выполнение действия;
   - проверка результата;
   - создание плана;
   - обнаружение проблемы;
   - перенос или удаление данных.
3. Простое отображение метрики без определённого смысла, provenance и дальнейшего использования не считается достаточным outcome.
4. Инфраструктурный workflow MAY завершаться проверяемым результатом надёжности: успешным backup, restore, integrity check или conflict resolution.
5. Функция без измеримого outcome не включается в release scope.

**Проверка:** acceptance test каждой пользовательской capability проверяет конечный outcome, а не только факт рендеринга или HTTP/IPC-ответа.

## I9. Результат, уверенность и качество измерения разделяются

1. Raw result MUST храниться отдельно от:
   - self-confidence;
   - evaluator confidence;
   - measurement quality;
   - model uncertainty;
   - data coverage.
2. Confidence MUST NOT изменять исходный result.
3. `unknown`, `not_applicable`, `invalid` и отсутствие наблюдения MUST NOT молча превращаться в zero.
4. Composite score MAY существовать только как именованная, версионированная и отключаемая derived projection.
5. Интерфейс MUST позволять отличить наблюдение от оценки модели и от гипотезы.
6. AI-generated confidence не является доказательством истинности и MUST хранить provenance.

**Проверка:** пересчёт модели или изменение confidence не изменяет raw observations; schema-тест запрещает смешанное поле «score × confidence» как source of truth.

## I10. Canonical-команды аудируемы и идемпотентны

1. Каждая command MUST иметь:
   - уникальный `command_id`;
   - `idempotency_key` и область его действия;
   - тип и версию command;
   - actor и origin;
   - device/client identity, если применимо;
   - preconditions, включая `expected_revision`, когда она существует;
   - время выдачи и приёма;
   - результат либо типизированную ошибку;
   - ссылку на audit record;
   - undo policy.
2. Повтор той же command с тем же idempotency key и эквивалентным payload MUST возвращать ранее зафиксированный результат и MUST NOT повторять изменение.
3. Повтор key с неэквивалентным payload MUST завершаться конфликтом идемпотентности.
4. Намеренное повторение пользовательского действия MUST использовать новый key.
5. Canonical mutation, audit event и sync outbox MUST фиксироваться одной транзакцией, когда данные являются syncable.
6. Read queries не обязаны создавать полный audit event. Доступ к чувствительным данным, outbound AI context и security-relevant reads MUST журналироваться согласно policy.
7. Derived processors MUST быть детерминированно повторяемыми либо хранить checkpoint, который предотвращает неконтролируемый повтор внешнего эффекта.
8. Audit MUST NOT содержать secrets и SHOULD минимизировать дублирование чувствительного содержимого.
9. Wall-clock timestamp MUST NOT быть единственным основанием порядка конкурирующих revisions или sync-событий.

**Проверка:** property-based и integration-тесты повторно доставляют commands, jobs и sync messages без дублирования canonical effects.

## I11. Undo сохраняет историю; необратимость является отдельным режимом

1. Каждая state-changing capability MUST объявлять одну из политик:
   - `reversible`;
   - `compensating`;
   - `irreversible`.
2. Для `reversible` undo MUST использовать новую command, смену head или новую revision.
3. Для `compensating` система MUST описывать, что именно компенсируется и какие внешние последствия невозможно отменить.
4. `irreversible` допускается только для purge, криптографического уничтожения ключа либо внешнего действия, которое технически невозможно отменить.
5. Необратимая операция MUST:
   - быть отделена от обычного edit/delete;
   - показывать точный scope;
   - выполнять preflight-проверку зависимостей, replicas и backups;
   - требовать явного усиленного подтверждения;
   - не выполняться скрыто, пакетно по умолчанию или по предложению ИИ без отдельного разрешения;
   - создавать минимальный audit receipt без уничтожаемого чувствительного body.
6. Обычный delete MUST быть обратимым tombstone или revision.
7. Undo MUST NOT удалять audit history.

**Проверка:** тест каждой command соответствует объявленной undo policy; irreversible workflow невозможно вызвать через обычный delete UI или общий AI tool.

## I12. Локальная работа является базовым режимом

1. Работа с уже локально доступными canonical данными MUST продолжаться без сети, хаба, телефона и AI provider.
2. К локально обязательным возможностям относятся:
   - чтение и изменение заметок;
   - просмотр уже загруженных документов;
   - локальный поиск после наличия или перестроения индекса;
   - revision history;
   - локальный export;
   - локальный backup и integrity check.
3. Внешняя недоступность MAY временно отключить только функции, которым объективно нужен внешний ресурс:
   - передачу sync;
   - OAuth;
   - облачный AI;
   - удалённый import/download;
   - cloud backup;
   - загрузку отсутствующего blob.
4. Offline commands MUST сохраняться локально и MAY синхронизироваться позднее.
5. Ошибка внешнего provider MUST NOT блокировать запуск приложения или доступ к локальным данным.
6. Core-функции MUST NOT требовать постоянной сетевой проверки лицензии или доступности компании-поставщика.
7. UI MUST явно показывать, какая функция недоступна из-за внешней зависимости, не объявляя локальные данные недоступными.

**Проверка:** offline acceptance suite запускается при полностью заблокированной сети и подтверждает работу локального core.

## I13. ИИ является недоверенным и заменяемым участником

1. Любая модель ИИ — локальная или внешняя — считается недоверенной.
2. ИИ MUST NOT получать:
   - прямой доступ к DB или blob store;
   - schema migration;
   - arbitrary code, SQL или shell execution;
   - secrets;
   - полномочия шире выданных capability scopes.
3. ИИ MAY читать данные только через разрешённые queries и Context Broker с outbound policy.
4. По умолчанию ИИ создаёт answer или proposal, а не mutation.
5. Mutation через ИИ допускается только как validated command draft с пользовательским подтверждением либо внутри заранее утверждённого restricted workflow с budget, scope, rollback/compensation и stop conditions.
6. Контент заметок, документов, web-страниц и tool outputs считается недоверенными данными и MUST NOT расширять полномочия модели.
7. Provider replacement MUST NOT менять capability contracts или canonical data model.
8. AI output, используемый как исторический результат, MUST хранить provider/model version, sources, tools, time, policy и uncertainty.
9. Отключение AI Layer MUST оставлять не-AI функции полностью работоспособными.

**Проверка:** security-тесты prompt injection, tool escalation, provider failure и повторной доставки не приводят к неразрешённой mutation.

## I14. Семантически значимые трансформации не скрываются

1. Raw input и raw observation MUST сохраняться без caps, winsorization, скрытых весов и изменения смысла.
2. Любая семантически значимая transformation MUST быть:
   - именована;
   - версионирована;
   - объяснима;
   - связана с исходными данными;
   - отключаема или заменяема без изменения raw source.
3. UI MUST отличать raw value от transformed или modelled value.
4. Lossless encryption, compression и storage encoding не считаются семантической transformation.
5. Schema MAY задавать явную canonicalization, например формат timestamp или Unicode normalization, только если правило документировано. Исходный ввод MUST сохраняться отдельно, когда canonicalization может изменить юридически, научно или пользовательски значимое содержание.
6. Redaction для outbound context MUST быть видимой в preview или audit metadata и MUST NOT изменять локальный original.
7. Display-only clipping или truncation MUST NOT записываться обратно как canonical value.

**Проверка:** любая отображаемая transformed величина предоставляет definition version и путь к raw source; отключение transformation не повреждает исходные данные.

## I15. Отказы локализуются в определённых failure domains

1. Архитектура MUST рассматривать как отдельные failure domains как минимум:
   - widget;
   - module;
   - processor/job;
   - derived index;
   - AI provider;
   - import adapter;
   - sync peer/device;
   - отдельный blob.
2. Ошибка одного из этих domains MUST NOT:
   - повреждать canonical state;
   - обходить transaction boundary;
   - блокировать независимые модули;
   - делать невозможными export и recovery незатронутых данных.
3. Неизвестный widget, отключённый модуль или отсутствующий derived index MUST приводить к явной локальной деградации, а не падению всего приложения.
4. Внешние вызовы MUST иметь timeout, cancellation, budget и ограниченный retry.
5. Jobs MUST иметь resource limits и failure state, доступный diagnostics.
6. Общий отказ Kernel, persistence, диска или ОС MAY затронуть всю систему; Конституция не обещает абсолютную доступность при отказе общей зависимости. Такой риск MUST компенсироваться транзакциями, integrity checks, backups и restore tests.
7. Граница отказа и ожидаемая деградация MUST быть частью acceptance suite компонента.

**Проверка:** fault-injection tests отключают каждый заявленный domain и подтверждают сохранность canonical state и доступность независимых функций.

## I16. Данные переносимы независимо от Nabla

1. Все несекретные предметные canonical data MUST иметь документированный machine-readable export.
2. Пользовательское содержание MUST дополнительно экспортироваться в человекочитаемом или общеупотребимом формате, где это возможно:
   - Markdown или plain text для заметок;
   - оригинальные файлы для документов и вложений;
   - JSON/CSV для структурированных observations;
   - manifest для IDs, relations, versions и provenance.
3. Export MUST включать достаточную семантику для интерпретации данных:
   - schema и semantic versions;
   - units;
   - timestamps и timezone rules;
   - relation types;
   - checksums;
   - missing-value semantics;
   - ссылки между manifest и файлами.
4. Ни один критический тип пользовательских данных MUST NOT существовать только в закрытом бинарном формате Nabla.
5. Secrets, device-local caches и transport state MUST NOT входить в обычный export.
6. Audit MAY экспортироваться отдельно в редактированном или минимизированном виде согласно privacy и security policy.
7. Backup и portable export являются разными продуктами:
   - backup оптимизирован для полного restore Nabla;
   - export оптимизирован для доступа к данным без Nabla.
8. Export MUST проверяться по checksums и SHOULD поддерживать повторный import без потери стабильных IDs и отношений.

**Проверка:** export открывается стандартными инструментами без установленной Nabla; manifest validator подтверждает полноту ссылок и checksums.

# 4. Сквозные правила

## 4.1 Приоритет сохранности над автоматизацией

При конфликте между скоростью автоматического действия и сохранностью canonical state система MUST выбрать отказ, proposal, preview или ручное подтверждение.

## 4.2 Privacy by construction

1. Сбор данных MUST быть минимально достаточным для активных loops.
2. Sensitivity, outbound policy и retention MUST определяться до включения сбора чувствительного поля.
3. Secrets MUST храниться вне основной canonical DB в OS-backed или отдельно защищённом secret store.
4. Logs и diagnostics MUST минимизировать чувствительное содержимое.
5. У пользователя MUST быть понятный путь к export, archive, deletion и purge.

## 4.3 Безопасная эволюция

1. Любое несовместимое изменение schema, protocol или public capability MUST иметь migration и compatibility plan.
2. Migration MUST быть повторяемой, журналируемой и проверяемой на копии либо после backup.
3. Нельзя объявлять производные данные canonical только ради упрощения миграции или sync.
4. Deprecation MUST иметь срок, владельца и путь сохранения пользовательских данных.

## 4.4 Экспериментальный код

Исследовательский spike MAY не реализовывать все инварианты только при одновременном выполнении условий:

- он изолирован от production canonical storage;
- использует синтетические или одноразовые копии данных;
- не включается в release;
- явно помечен как disposable;
- его результатом является проверенное знание или ADR, а не неявный production dependency.

Spike MUST NOT использоваться как оправдание переноса неконституционного кода в основную систему.

# 5. Иерархия проектных решений

Документы и реализация подчиняются следующему порядку:

1. `CONSTITUTION.md`;
2. `ARCHITECTURE.md`;
3. принятые ADR;
4. `DATA-CLASSIFICATION.md`, capability/module/loop contracts и protocol specifications;
5. module specifications, Data Catalog, schemas и DDL;
6. ROADMAP и release plans;
7. код и тесты.

ADR уточняет решение внутри Конституции, но MUST NOT отменять или ослаблять её требование.

Если два подчинённых документа расходятся:

1. расхождение регистрируется как defect;
2. реализация зависимого участка приостанавливается, если существует риск потери данных, нарушения безопасности или несовместимой schema;
3. принимается ADR либо поправка к вышестоящему документу;
4. обновляются зависимые документы, migrations и tests;
5. только после этого расхождение считается устранённым.

Молчаливое признание кода новым источником истины запрещено.

# 6. Изменение Конституции

Конституция является устойчивой, но не буквально неизменяемой. Ошибочное правило не должно сохраняться только из-за ранней формулировки.

## 6.1 Виды изменений

- **Patch:** редактура и уточнение без изменения множества разрешённых архитектур.
- **Minor:** новое требование либо усиление существующего без отмены основной гарантии.
- **Major:** ослабление, удаление, переопределение инварианта или несовместимое изменение гарантии пользователю.

## 6.2 Обязательная процедура

Изменение MUST оформляться отдельным `CA-###` — Constitutional Amendment — и содержать:

1. точную изменяемую формулировку;
2. наблюдаемую проблему;
3. причины, по которым обычного ADR недостаточно;
4. альтернативы и причины отказа от них;
5. влияние на данные, security, privacy, offline mode, portability и AI permissions;
6. перечень затронутых документов и компонентов;
7. migration и compatibility plan;
8. новые или изменённые conformance tests;
9. план rollout и, где возможно, rollback;
10. явное утверждение владельцем проекта.

Ни агент, ни отдельный модуль, ни срочность milestone не могут изменить Конституцию самостоятельно.

Временное исключение в production release запрещено. Если требование невозможно выполнить, функция остаётся экспериментальной, удаляется из release scope либо инициируется Constitutional Amendment.

# 7. Конституционная совместимость

Компонент считается совместимым только если для применимых инвариантов существует проверяемое доказательство.

## 7.1 Conformance Matrix

Каждый официальный модуль и protocol MUST иметь таблицу:

```text
invariant_id
applicability
implementation_mechanism
tests
known_limits
owner
```

`not_applicable` MUST сопровождаться причиной. Отсутствие реализации или теста не может маскироваться как `not_applicable`.

## 7.2 Минимальные архитектурные проверки

CI и release review MUST проверять как минимум:

1. отсутствие прямых canonical DB writes вне разрешённого boundary;
2. запрет обычного изменения immutable facts;
3. целостность revision chains и conflicts;
4. rebuild derived state;
5. semantic versioning contracts;
6. manifests, permissions и trusted module policy;
7. наличие loops либо технического обоснования полей;
8. outcome-based acceptance tests;
9. разделение raw result и uncertainty;
10. idempotency повторной доставки;
11. соответствие undo policy;
12. offline operation;
13. AI permission and prompt-injection boundaries;
14. provenance transformations;
15. fault isolation;
16. portable export validation.

## 7.3 Release rule

Release MUST NOT считаться прошедшим gate, если известное нарушение Конституции затрагивает canonical data, security, privacy, portability или необратимое действие.

Для некритического нарушения SHOULD быть создан blocking defect с владельцем и сроком; исключение из gate возможно только если требование фактически неприменимо и это доказано в Conformance Matrix.

# 8. Зафиксированные разрешения прежних неоднозначностей

Настоящая версия принимает следующие решения:

1. **Command boundary применяется ко всему предметному canonical state.** Audit/evidence records создаёт только Kernel Audit Service; derived и operational writes разрешены только зарегистрированным processors и Kernel Services. Ни один из этих путей не даёт права произвольно менять предметные canonical data.
2. **Loop обязателен для предметной информации.** Служебные поля вместо искусственного пользовательского loop получают техническое обоснование, владельца, consumer и retention.
3. **Не все действия обратимы.** Обычные mutations сохраняют историю; purge и объективно необратимые внешние эффекты выделяются в отдельный усиленно подтверждаемый режим.
4. **Offline-гарантия относится к локальным данным и core-функциям.** Она не обещает работу OAuth, cloud AI, передачи sync и загрузки отсутствующих файлов без сети.
5. **Локальная деградация имеет границы.** Отказ общей persistence/OS зависимости может затронуть всю систему, но отказ модуля, widget, processor, provider или peer не должен этого делать.
6. **Runtime code generation запрещён.** Будущие доверенные устанавливаемые модули не запрещены навсегда, но требуют отдельной защищённой модели установки и не получают неограниченных полномочий.
7. **Portable export охватывает все несекретные предметные canonical data.** Derived, transport, device-local state и secrets не выдаются за пользовательский источник истины.
8. **Конституция изменяема только через усиленную процедуру.** Обычный ADR не может молча ослабить инвариант.
