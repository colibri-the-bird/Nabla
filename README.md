# Nabla ∇

Nabla — локально-первичная персональная система для работы со знаниями, обучением и личными данными.

Проект объединяет:

- базу Markdown-заметок со ссылками, свойствами и историей изменений;
- библиотеку учебных материалов и PDF-читалку с аннотациями;
- модульную систему интерфейсов, форм, виджетов и аналитики;
- инструменты для отслеживания обучения, повторения материала и анализа прогресса;
- синхронизацию между компьютером и мобильными устройствами;
- управляемое взаимодействие с облачными и локальными моделями ИИ.

Архитектура Nabla строится вокруг нескольких принципов:

- данные принадлежат пользователю и сохраняются локально;
- все смысловые изменения проходят через проверяемые команды, журналируются и заранее объявляют режим отмены, компенсации либо необратимости;
- первичные данные не искажаются аналитическими формулами;
- каждый собираемый тип данных должен иметь понятного потребителя и практическое назначение;
- функциональность расширяется через типизированные модули и возможности, а не через произвольную генерацию кода;
- ИИ не получает прямого доступа к базе данных и работает только через ограниченные инструменты, предложения, подтверждаемые команды и заранее разрешённые workflows с конечными полномочиями.

Разработка разделена на три основные версии:

- **v1:** модульное ядро, Desktop-приложение, заметки, документы и PDF;
- **v2:** система обучения, аналитика, мобильное приложение и синхронизация;
- **v3:** интеграция ИИ, поддержка OAuth, API и локальных моделей, анализ данных и безопасное изменение конфигурации системы.

## Разработка с ИИ-агентами

Подробные архитектурные и модульные спецификации являются нормативным источником истины, но не должны целиком загружаться в контекст каждого агента. Во время реализации используется принцип progressive disclosure: агент получает только относящиеся к текущей задаче документы и разделы, оставляя контекст для исходного кода, тестов, результатов команд и рассуждений.

Подготовительный agent/tooling слой уже включает:

- `AGENTS.md` — короткую постоянную инструкцию и точку входа;
- `roadmap/BOOTSTRAP.md` и отдельные YAML task cards — подготовительный DAG;
- `tools/spec_slice.py` — безопасное извлечение нормативного контекста;
- `tools/nabla_nav.py` — validation, context, scope и evidence workflow;
- GitHub checks для navigation, task scope, evidence и living spec lock.

Production `ROADMAP.md` намеренно остаётся заблокированным до утверждения
применимых specifications, закрытия обязательных ADR/spikes, готовности v1 DDL
и backup/recovery foundation.

Навигация строится по `SPEC-NAVIGATION.md`: нормативные разделы получают стабильные selectors вида `CAP:11.4` или `DOC:11`, task cards Roadmap ссылаются на context packs и impact tags, а generated `spec-index.json` вместе с read-only slicer извлекает точный текст только необходимых sections. При расширении scope tags автоматически добавляют cross-cutting требования к canonical writes, blobs, relations, sensitivity, export, purge и другим затронутым boundaries. Неразрешимый или устаревший selector блокирует задачу.

Roadmap, summaries и agent instructions не переопределяют нормативные спецификации и не дублируют их содержимое. При конфликте действует соответствующий нормативный документ; при обнаружении пробела агент должен остановить спорное изменение и инициировать уточнение спецификации или ADR. Такой подход позволяет использовать подробную документацию выборочно, не перегружая контекстное окно и не создавая вторую независимо редактируемую архитектуру.

Цель проекта — создать долговечную персональную операционную среду, которая сможет развиваться и усложняться без потери данных, управляемости и архитектурной целостности.
